第四节继续往下：

模型提出的 toolCall，怎样安全、可解释地进入真正的工具函数？工具执行失败、文件修改和取消分别意味着什么？

这一节是从“会调用模型”走向“会开发 Agent”的关键。

先记住三个判断：

  1. 参数能解析，不等于参数合法。
  2. 参数合法，不等于动作被授权或业务正确。
  3. 工具返回错误，不等于副作用没有发生。

本次依据已核对的 Pi 提交 eb326d2，只做源码解释，没有修改文件或执行测试。

一、先看完整的工具执行链

假设模型生成：

{
  "type": "toolCall",
  "id": "call_1",
  "name": "read",
  "arguments": {
    "path": "package.json"
  }
}

它表达的是：

调用 read，参数为 package.json。

模型并没有直接执行文件读取。

Pi 接下来走：

按名称查找工具
    ↓
prepareArguments：兼容参数表示
    ↓
validateToolArguments：运行时校验
    ↓
beforeToolCall：执行前检查
    ↓
tool.execute：真实动作
    ↓
afterToolCall：结果处理
    ↓
生成 ToolResultMessage
    ↓
结果回灌给模型

核心源码：

  • 工具准备：agent-loop.ts:694–777
  • 执行与结果处理：821–910
  • 生成工具结果消息：930–949

为什么分成这些阶段？

因为每个阶段解决的问题不同：

阶段 回答的问题
工具查找 程序是否真的提供这个工具？
参数准备 模型的参数表示能否转换为约定形式？
Schema 校验 字段和类型是否符合要求？
前置 hook 在当前条件下是否允许执行？
execute 实际动作是否完成？
后置 hook 什么结果应该返回，是否需要处理？
ToolResult 模型如何关联和理解执行反馈？

如果把这些问题全部塞进一个工具函数，会很难判断错误发生在哪里，也很难复用统一控制。

二、工具声明和工具实现，为什么要区分？

1. 工具声明给模型看

它告诉模型：

工具叫什么？
什么时候使用？
参数怎么填写？

例如 read 的参数 schema：

read.ts:14–18

const readSchema = Type.Object({
    path: Type.String({
        description: "Path to the file to read (relative or absolute)"
    }),
    offset: Type.Optional(Type.Number({
        description: "Line number to start reading from (1-indexed)"
    })),
    limit: Type.Optional(Type.Number({
        description: "Maximum number of lines to read"
    })),
});

Type.Object() 创建的是运行时可以使用的 schema 对象。

它既可以作为模型的工具参数说明，也可以被本地验证器使用。

2. 工具实现给程序执行

核心 AgentTool 在声明之外，还提供：

execute(
    toolCallId,
    params,
    signal,
    onUpdate
)

定义见：

types.ts:466–498

这才是真正执行：

  • 文件读取；
  • 文件修改；
  • HTTP 请求；
  • 数据库操作；
  • 外部命令；

的入口。

为什么不能让模型直接指定任意函数执行？

模型的输出不可信。它可能：

  • 编造工具名称；
  • 拼错参数；
  • 使用不存在的路径；
  • 提出不允许的动作。

因此程序必须维护一套实际可执行的工具集合。

模型只是在这套能力上提出调用意图，不应该因为输出了一个名字就获得任意执行权。

三、prepareToolCall()：把“可以执行”和“立即返回错误”分开

打开：

agent-loop.ts:708–777

先看工具查找：

const tool = tools.find((t) => t.name === toolCall.name);

if (!tool) {
    return {
        kind: "immediate",
        result: createErrorToolResult(`Tool ${toolCall.name} not found`),
        isError: true,
    };
}

如果模型请求：

delete_entire_project

但程序没有提供这个工具，就直接返回错误。

不会动态执行同名函数，也不会因为模型说“这是必要操作”就补造能力。

为什么返回 kind: "immediate"？

这个函数有两类结果。

情况 A：准备失败，不执行

{
    kind: "immediate",
    result: 错误结果,
    isError: true
}

情况 B：准备完成，可以进入执行阶段

{
    kind: "prepared",
    toolCall,
    tool,
    args: validatedArgs
}

这是一个带标签的联合结构。调用者通过 kind 就知道下一步：

immediate → 不执行，直接形成工具结果
prepared  → 调用 execute

设计收益：执行阶段不需要重复判断工具是否存在、参数是否已通过准备。

这里的 prepared 是“经过准备”，不是“工具已经执行成功”。

四、参数准备与参数验证：两者为什么不是一回事？

1. prepareArguments 处理表示兼容

模型有时传回：

{
  "edits": "{\"oldText\":\"foo\",\"newText\":\"bar\"}"
}

或者：

{
  "edits": {
    "oldText": "foo",
    "newText": "bar"
  }
}

但工具约定的结构是：

{
  "edits": [
    {
      "oldText": "foo",
      "newText": "bar"
    }
  ]
}

Pi 的 edit 工具在：

edit.ts:103–134

将部分明确的兼容表示转换为标准结构，例如：

  • JSON 字符串解析为数组；
  • 单项对象包装成数组；
  • 兼容旧式单项参数。

通用准备阶段调用它：

const preparedArguments = tool.prepareArguments(toolCall.arguments);

见：

agent-loop.ts:694–705

这里的设计取舍是什么？

收益是：不因模型输出的可兼容格式差异，轻易让整个任务失败。

代价是：转换逻辑会增加复杂性，甚至可能改变意图。

所以它应该处理明确的表示兼容，不能悄悄把：

读取文件

转换成：

修改文件

也不能因为想减少错误，就给所有缺失业务字段填猜测值。

2. validateToolArguments 检查转换后的参数

随后：

const validatedArgs = validateToolArguments(tool, preparedToolCall);

见：

agent-loop.ts:725–727

prepareArguments 负责整理表示，validation 负责检查结构。 整理完仍然要验证。

五、为什么 TypeScript 类型不能代替运行时校验？

工具函数可能写：

params: {
    path: string;
}

这帮助开发者在写代码时检查类型。

但是模型返回的是外部 JSON：

{}

TypeScript 类型不会在程序运行时自动把这个 JSON 拦下来。

类似：

const params = input as ReadToolInput;

也只是类型断言，不会检查 path 是否存在。

因此需要 schema 验证。

Pi 验证器的实际过程

打开：

validation.ts:317–350

const args = structuredClone(toolCall.arguments);

normalizeOptionalNulls(args, tool.parameters);
Value.Convert(tool.parameters, args);

const validator = getValidator(tool.parameters);

// 部分普通 JSON Schema 的转换路径

if (validator.Check(args)) {
    return args;
}

// 格式化错误并抛出

主要步骤：

  1. 克隆参数；
  2. 处理部分可选字段的 null；
  3. 按 schema 尝试类型转换；
  4. 取得编译后的验证器；
  5. 检查参数；
  6. 不通过则产生带字段位置的错误。

为什么先克隆？

验证过程中可能发生归一化和转换。

因此：

模型原始 arguments

与：

execute 收到的 args

可能不同。

保留原始参数，有助于解释：

模型实际传了什么？
程序转换了什么？
最终执行了什么？

注意，之前的工具专用 prepareArguments 仍可能修改原对象；不能据此说整个准备过程绝对不修改原始输入。

为什么处理可选 null？

有些模型会为没有填写的可选字段生成：

{
  "path": "package.json",
  "offset": null
}

如果 schema 不允许 null，但该字段又不是必填，Pi 可以把它归一化为“未提供”，而不是让调用仅因这个表示问题失败。

规则见：

validation.ts:240–269

为什么缓存验证器？

编译 schema 有成本，同一工具会被多次调用。

Pi 使用 WeakMap 缓存对应验证器：

validation.ts:271–280

这样不必每次重新编译同一份 schema。

Schema 通过之后还缺什么？

例如：

{
  "path": "/某个敏感文件"
}

结构可能完全合法：

  • path 存在；
  • 类型是字符串。

但这不证明用户允许读取它。

所以：

结构校验不是资源授权，也不是业务验收。

六、beforeToolCall：执行前的控制点

参数验证后：

const beforeResult = await config.beforeToolCall(
    {
        assistantMessage,
        toolCall,
        args: validatedArgs,
        context: currentContext,
    },
    signal,
);

如果返回：

{
    block: true,
    reason: "当前任务不允许修改文件"
}

就不进入 execute()。

源码：

agent-loop.ts:728–755

这个位置适合接入：

  • 参数涉及的资源范围检查；
  • 业务前置条件；
  • 人工审批；
  • 风险规则；
  • 自定义访问策略。

这些是可接入能力，不是 Pi 默认已经提供一整套生产权限系统。

一个必须知道的当前行为：hook 可以修改已验证参数

例如：

schema：value 必须是字符串
原始参数：{ value: "hello" }
验证：通过
before hook：把 value 改成 123
execute：收到 123

普通 core 在 before hook 后没有自动再次校验。

已有测试明确覆盖：

agent-loop.test.ts:528–587

测试最后断言：

expect(executed).toEqual([123]);

为什么这点值得学？

因为不能认为：

进入 execute 的参数以前验证过

就代表：

进入 execute 的这个最终值一定符合 schema

中间的 hook 也是信任边界的一部分。插件修改参数时，需要自己维护校验和意图一致性。

这里是源码事实，不是在建议你修改校验边界。

七、真正执行：execute() 的四个参数分别做什么？

打开：

agent-loop.ts:821–857

核心：

const result = await prepared.tool.execute(
    prepared.toolCall.id,
    prepared.args,
    signal,
    onUpdate,
);
参数 用途
toolCallId 关联本次调用、进度和结果
args 准备后的执行参数
signal 合作式取消
onUpdate 工具执行中的进度反馈

为什么工具也需要进度更新？

模型文本生成可能很快，但工具可能执行较久，例如：

下载数据
→ 分析
→ 执行测试

onUpdate 可以报告过程，不需要等最终结果。

Pi 将它映射成 tool_execution_update：

agent-loop.ts:779–787

但：

工具进度不是最终工具结果，也不证明任务完成。

执行完成后再调用更新回调，当前 core 会忽略它；执行期间产生的更新 Promise 会被等待，然后进入后处理。

durationMs 测量了什么？

这里主要计量 execute() 的耗时。

它不包含前置 hook 和后置 hook；也不能当作整个 Agent 任务耗时。

测量时先明确边界，避免把多个不同指标都叫“工具延迟”。

八、错误怎样处理：不是所有失败都结束 Agent

1. execute 抛异常

例如：

throw new Error("File not found");

通用执行器会把异常转换成：

错误工具结果

而不是默认让整个 Agent 崩溃。

2. execute 返回显式错误

例如：

{
    content: [{ type: "text", text: "操作被业务规则拒绝" }],
    details: {},
    isError: true,
}

同样作为错误结果处理。

3. 只在文字里说失败，不会自动设置错误标记

下面的结果：

{
    content: [{ type: "text", text: "失败了" }],
    details: {},
}

在 core 看来，不会仅因为出现“失败”这个词就自动成为错误结果。

所以工具契约要求：

失败时抛异常，或明确返回 isError: true。

各阶段失败的区别

情况 execute 是否调用 after hook 是否调用
工具不存在 否 否
参数校验失败 否 否
before 返回 block 否 否
before 抛错 否 否
execute 抛错 是 有配置时会调用
execute 正常返回 是 有配置时会调用

这张表很重要。它帮你判断：

只是请求被拒绝？
还是动作已经开始，后来失败？

九、afterToolCall：处理结果，但不会撤销动作

打开：

agent-loop.ts:859–910

它接收：

调用、参数、结果、错误标记、当前上下文

可以改写：

  • content；
  • details；
  • structuredContent；
  • isError；
  • usage；
  • terminate。

这些是按字段替换，不是深度合并。

为什么需要后处理？

工具可能返回：

  • 过长内容；
  • 需要脱敏的数据；
  • 图片；
  • 底层错误；
  • 不适合模型直接阅读的结构。

后处理可以调整最终反馈。

Pi 产品层把扩展的 tool_call 和 tool_result 接到前后 hooks：

agent-session.ts:644–724

为什么替换 content 时可能删除 structuredContent？

如果文字已经变成：

数据已脱敏

但结构化结果仍保留原始敏感字段，两种结果就不一致。

所以当前逻辑在替换 content 而没有提供对应 structuredContent 时，会丢弃旧 structuredContent。

后置 hook 失败意味着什么？

假设：

文件写入成功
→ after hook 抛错
→ 最终工具结果被标记为错误

文件不会因此自动恢复原样。

后处理发生在动作之后，不能作为回滚机制或执行前授权机制。

十、工具返回的三个字段，为什么给不同使用者？

定义：

types.ts:423–445

content：给模型看

例如：

Successfully replaced 2 block(s) in example.txt.

用于下一轮模型判断。

details：给 UI、日志或程序记录

例如 edit 返回：

{
    diff,
    patch,
    firstChangedLine
}

见：

edit.ts:201–210

模型不需要接收所有展示细节，但 UI 需要知道改了哪里。

structuredContent：给程序调用者

例如某个工具供 codemode 脚本调用，需要获得稳定结构，而不是解析一段自然语言。

声明 outputSchema 不代表普通 core 在这里自动验证输出。 当前执行管线没有因此增加统一输出校验。

最终 ToolResultMessage 带上：

toolCallId
toolName
content
details
isError
timestamp

见：

agent-loop.ts:930–943

这样模型可以把结果关联到正确的工具调用。

十一、具体工具一：read 怎样读取与限制输出？

打开：

read.ts:86–216

文本路径大致是：

解析文件路径
→ 检查可读
→ readFile 取得 Buffer
→ 转 UTF-8 文本
→ 按 offset/limit 选行
→ 按行数和字节预算截断
→ 返回内容与继续读取提示

1. offset 为什么减一？

用户看到的是从 1 开始的行号，数组从 0 开始。

offset=3
→ allLines[2] 开始

对应：

read.ts:154–175

2. limit 限的是模型输出，不是全部文件 I/O

代码先：

const buffer = await ops.readFile(absolutePath);

再：

allLines.slice(startLine, endLine)

因此：

limit=20

不等于：

底层只读20行，内存只存20行。

它主要减少返回给模型的内容。面对巨大文件，还需要考虑实际读取和内存成本。

3. 为什么截断后告诉模型 next offset？

如果文件没有读完，只返回前半部分而不说明，模型可能误以为已经掌握全文。

Pi 会附加类似：

Showing lines 1–2000 ...
Use offset=2001 to continue.

源码：

read.ts:176–199

这是一个重要的工具设计原则：

结果不完整时，要明确告诉调用者缺了什么、怎样继续，不要伪装成完整证据。

4. 为什么 operations 可以替换？

ReadOperations 把底层读取动作作为接口：

read.ts:44–69

默认是本地文件系统，也可以替换为：

  • 远程文件读取；
  • 受限执行环境；
  • 测试替身。

这和 StreamFn 注入模型是相同思想：

保留工具语义，替换实际执行后端。

但“可替换后端”不等于默认已经有沙箱。

十二、具体工具二：edit 为什么基于同一份原始文件？

打开：

edit.ts

当前参数是：

{
  "path": "example.txt",
  "edits": [
    {"oldText": "foo\n", "newText": "foo bar\n"},
    {"oldText": "bar\n", "newText": "BAR\n"}
  ]
}

原文件：

foo
bar
baz

正确结果：

foo bar
BAR
baz

如果逐项改完再重新匹配，会发生什么？

第一项造出了一个新的 bar：

foo bar
bar
baz

若第二项基于修改后的文本搜索，可能匹配到第一项新生成的内容，导致位置或唯一性发生变化。

所以 Pi 的规则是：

所有 edits 先在同一份原始内容中定位，再统一应用。

算法：

edit-diff.ts:300–361

主要步骤：

  1. 统一行结束表示；
  2. 禁止空 oldText；
  3. 查找每个 oldText；
  4. 检查唯一性；
  5. 记录匹配位置；
  6. 检查匹配区域不重叠；
  7. 统一生成新内容；
  8. 最后才写文件。

为什么从后向前替换？

如果先替换文件前面的内容，长度变化会让后面的位置偏移。

先改后面的区域
→ 前面区域的原偏移仍然有效

因此定位后按逆序应用，可保持原始偏移。

为什么禁止重叠 edits？

例如：

原文件：one / two / three

编辑A：替换 one+two
编辑B：替换 two+three

两项同时声明修改 two，存在冲突。

Pi 不猜先后优先级，直接要求合并或拆成不重叠区域。

为什么一项失败，不会先写一半？

因为实际 writeFile() 在全部匹配与检查之后。

测试：

tools.test.ts:425–441

第一项合法、第二项不存在时，测试要求原文件保持不变。

但这只是匹配失败时不会部分应用，不是崩溃安全的文件事务。 写入期间的失败、多文件操作或外部服务，不在这个保证内。

十三、exact 与 fuzzy：容错怎样做到不随意乱改？

Pi 先找 exact match，找不到再尝试受控字符归一化匹配：

edit-diff.ts:201–244

例如处理：

  • 智能引号；
  • Unicode 空格；
  • 特定破折号；
  • 行尾空白。

这不是“意思相似就替换”，也不是让另一个模型猜目标段落。

它是确定性的文本归一化。

为什么需要？

模型可能把文件中的智能引号写成普通引号。纯字符差异会造成合理修改无法定位。

为什么又要保持严格？

过强的模糊匹配可能把多个位置归一化成相同内容。

因此还要验证唯一性。当前出现次数检查也使用 fuzzy-normalized 形式，见：

edit-diff.ts:247–250

收益是容忍明确表示差异；代价是匹配空间更复杂，需要防止歧义。

另外，工具还会去掉 BOM 后匹配，并尽量恢复原有换行格式：

edit.ts:190–198

避免为了一个局部修改，把文件格式一起改掉。

十四、为什么 Node 单线程仍然需要文件修改队列？

假设两项 edit 并发：

A 读到：alpha / beta
B 读到：alpha / beta

A 写出：ALPHA / beta
B 写出：alpha / BETA

最终 B 可能覆盖 A 的修改。

Node 的 JavaScript 执行是单线程，不代表：

所有异步读写操作自动串行。

多个 async 操作会在 await 处交错。

Pi 的解决办法

edit 将整个读—改—写过程包在：

withFileMutationQueue(absolutePath, async () => {
    // 检查、读、计算新内容、写
});

见：

edit.ts:159–212

队列实现：

file-mutation-queue.ts

它按路径维护 Promise 链：

操作A等待之前的操作
→ 执行A
→ finally释放
→ 操作B才开始

已有文件会尝试用 realpath 作为键，让符号链接别名尽量共享同一队列。

为什么只锁写操作不够？

如果 A、B 已经同时读了旧内容，只把最后两次写串行，B 仍会写出基于旧版本计算的结果。

所以需要串行化：

读当前内容 → 计算修改 → 写入

这一整段。

能保证什么，不能保证什么？

  • 同进程、参与该队列、针对同一个键的修改可串行；
  • 不同文件仍可并行；
  • 不是跨进程文件锁；
  • 外部编辑器、其他子 Pi 或不走这队列的动作不受它统一保护。

不要把一个进程内队列说成完整的并发文件系统协调。

十五、最重要的失败边界：取消不是回滚

edit 的源码在每个主要 await 后检查 signal：

await ops.writeFile(absolutePath, finalContent);
throwIfAborted();

见：

edit.ts:163–199

所以可以出现：

开始 writeFile
    ↓
用户取消
    ↓
在途 writeFile 完成
    ↓
signal 检查发现取消
    ↓
工具返回 aborted 错误

此时文件已经变了。

为什么不在 abort listener 中立即释放队列？

如果立即 reject 并释放：

A 的写仍在进行
→ B 开始读写
→ A 后来才落盘

可能破坏顺序。

Pi 选择等在途操作完成，再释放修改队列。

测试：

file-mutation-queue.test.ts:221–273

测试明确要求：

  • A 写期间取消；
  • B 仍要等待；
  • A 完成后报取消；
  • B 读到 A 已发生的修改后继续；
  • 最终两项修改都体现在文件中。

read 的取消为什么可以不同？

read 没有文件修改副作用，可以较早向调用者返回取消，并避免把后续结果交出去。

但当前底层 readFile() 没因为这个包装层取消就一定被物理中断。

取消策略取决于操作语义，不能所有工具统一写一个 Promise.race 就认为安全。

这与业务工具有什么关系？

订单、通知、付款工具也会遇到：

外部动作成功
→ 超时或取消
→ 本地结果报错

要判断是否重试，必须查询效果、使用幂等键或进行人工确认，不能直接把“报错”解释为“没做”。

十六、把一项 edit 从头到尾串起来

正常路径：

模型生成完整 toolCall(edit)
    ↓
当前可执行集合查到 edit
    ↓
prepareEditArguments 整理表示
    ↓
schema 校验参数结构
    ↓
beforeToolCall 准入
    ↓
进入 execute
    ↓
validateEditInput 检查非空 edits
    ↓
解析路径
    ↓
进入同文件修改队列
    ↓
检查可读可写
    ↓
读当前文件
    ↓
BOM与换行处理
    ↓
定位全部 edits，检查唯一和不重叠
    ↓
计算全部新内容
    ↓
写文件
    ↓
检查取消
    ↓
生成 diff、patch和工具结果
    ↓
afterToolCall
    ↓
ToolResult 回灌
    ↓
模型根据结果继续

这条链里有几种不同的“正确”：

JSON结构正确
→ 修改位置正确
→ 文件写入完成
→ 修改实现需求
→ 测试与验收通过

前一项不会自动保证后一项。

Pi 的 edit 工具可靠地约束了一部分修改动作，但不会因为替换成功，就证明代码功能正确。

正确方向是检查真实文件、diff、执行端记录等，而不是只读错误标记。

面试回答模板

Pi 将工具处理分为准备、执行和结果处理。先按名称查找可执行工具，整理参数并做运行时 schema 校验，再进入前置 hook 和 execute。工具错误作为可关联的 ToolResult 回灌，后置 hook可以处理结果，但不能撤销已发生动作。read 的输出预算不等于底层资源预算；edit 先在同一原始文件中定位全部唯一、不重叠替换，再统一写入，并用进程内队列避免异步读改写错序。取消是合作式通知，写期间取消仍可能留下副作用，最终工具成功也不等于业务验收通过。

能讲清“结构、授权、执行效果、结果反馈、业务验收”这五层区别，并解释原始文件编辑和写期间取消两个反例，就掌握了第四节最重要的设计思想。
